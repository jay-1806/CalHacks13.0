# Current State Audit - ScreenTutor AI

## 1. Executive Summary

This document evaluates the existing code and files in the ScreenTutor AI repository to establish a clear audit of the current capabilities, gaps, fake integrations, and fragile systems.

### What Currently Works
- **Electron Shell**: Multi-window architecture is running, with a `mainWindow` (representing the Chat Panel or Floating Button depending on size) and a transparent, always-on-top, click-through `overlayWindow`.
- **Screen Capture Native Stub**: Uses `desktopCapturer` to fetch the primary screen base64 thumbnail, with a simple window title blocklist to enforce privacy check.
- **Global Hotkey**: The shortcut `CommandOrControl+Shift+E` is registered in Electron to trigger the capture and notify the main window UI.
- **Shared Zod Schemas**: Full Zod schema validations are established for tutoring requests (`TutorInput`, `TutorResponse`), drawing commands (`DrawingCommand`), learner memory, research parameters, and actions.
- **Local Specialist Agent Routing**: Local typescript agent classes dispatch based on hardcoded rules or simple regex patterns.
- **Redis Integration Fallback**: `RedisMemoryService` is set up with an automatic,Map-based `InMemoryService` fallback when Redis is unreachable or missing from environment setup.

### What is Fake
- **Visual Intelligence**: The AI providers (`anthropic`, `gemini`, `openai`) are completely stubbed out. They return static mocks from `MockAIProvider` matching specific string keywords in the user's question, rather than running multi-modal vision prompts.
- **Web Research**: Browserbase is represented by a mock wrapper that returns standard dummy research responses.
- **Desktop Actions (Co-drive)**: The Simular integration is a mock stub. It returns a single static click action and does not perform real operating system clicks, key presses, or desktop control.
- **Agentverse Discovery**: The Agentverse client is stubbed and does not register local agents or connect to remote networks.
- **Sentry and Arize**: These integrations are completely fake (non-existent). They are not present in dependency files, and no telemetry or error trapping pipelines are initialized.

### What is Fragile
- **Coordinates & Responsive Layouts**: The drawing overlay converts coordinates assuming a simple `vw`/`vh` ratio. On multi-monitor or non-standard aspect ratio screens, coordinates will skew or display incorrectly.
- **Window Positioning**: Changing the window size via `setMainSize` (380x520 to 60x60) leaves the window in its default position. When collapsed to 60x60, it shows a white or black background box because transparency is disabled on `mainWindow`.
- **Coordinate Mapping and Offsets**: Point coordinates generated by the mock provider or real AI will place Buddy directly on top of the highlighted element instead of offset smoothly.

### What is Overbuilt
- **Standard Chat UI**: The interface mimics a generic chat container rather than a sleek, cursor-native companion.
- **Unused AI Providers**: The repository contains boilerplate files for OpenAI and Gemini providers, which are outside our target sponsor scope.

### What is Missing for a Clicky-like Experience
- **Cursor Anchoring**: Buddy does not track or align to the user's cursor.
- **Point Tag Parsing in Speech**: Spoken text is rendered statically. The UI does not parse embedded point indicators (`<point x="..." y="..."/>`), strip them out, or command Buddy to fly to the target coordinate.
- **Buddy Flight Animation**: The main window snap positions directly rather than executing a smooth, premium flight animation across the desktop screen.
- **Co-drive Action UI**: The Chat Panel lacks any UI cards or approval buttons to view or approve proposed actions.

## 2. Product Critique

### Does this feel like a cursor companion or a regular chatbot?
**Regular Chatbot.** Right now, it is a boxy sidebar window displaying a chat log. It does not feel cursor-native or integrated. It needs to live right next to the cursor, collapse into a tiny transparent emblem, and move near the target content during explanations.

### Does the user get magic in the first 20 seconds?
**No.** The user is presented with a standard chat box. Pressing the hotkey captures the screen but doesn't feel like a spatial assistant drawing on their real workspace because Buddy does not move, and the SVG overlays are disconnected from the user's active focus area.

### Does the app point at the right thing on the screen?
**No.** The mapping assumes hardcoded mock coordinates or standard viewports. Since the screen dimensions are not mapped correctly to layout bounds and multi-monitor setups are ignored, overlays will miss the exact learning targets on standard pages.

### Is the tutor teaching or just answering?
**Just answering.** The current mock provider simply dumps solutions, and the Hint mode returns a static ladder instead of dynamic progressive hints that react to what the student is looking at.

### Are sponsor integrations meaningful or just labels?
**Just labels.**
- Redis is mapped to standard session storage rather than concept memory.
- Claude is stubbed out.
- Browserbase research and Simular actions return canned text.
- Sentry and Arize are absent.

## 3. Technical Critique

### Desktop Shell
The desktop shell runs standard Electron windows. The `mainWindow` is configured with `transparent: false` and `frame: false`. This causes a gray/white square border to appear when it collapses into the floating button, destroying the overlay aesthetics.

### Global Hotkey
The hotkey `CommandOrControl+Shift+E` is registered, but it has no collision protection. If another system service registers it, Electron silently logs a warning and fails.

### Screen Capture
Uses `desktopCapturer` which takes high-resolution thumbnails. It defaults to the first source, which is fragile in multi-monitor setups. It checks window titles using an insecure string-match denylist.

### Overlay Behavior
The transparent overlay window is set to ignore mouse events. The SVG canvas renders overlays dynamically, but lacks smooth animation transitions.

### Multi-Monitor Support
Completely unsupported. The screen capture defaults to `sources[0]`, and coordinate conversions do not map to the primary screen versus extended screens.

### Coordinate Mapping
The coordinate system is 0-1 normalized, but mapped to CSS `vw` and `vh` variables in React. If the overlay window size differs from the primary screen viewport, annotations will not match.

### Voice Input & TTS
Voice input is missing. Text-to-speech (TTS) is missing. Explanations are only shown in standard text bubbles.

### Claude Provider
Currently a stub that prints a fallback log and calls the `MockAIProvider`.

### Mock Provider
Contains hardcoded checks for keywords (`distribute`, `derivative`, `u-sub`, `graph`). It is highly rigid and does not support varying layouts.

### Redis Memory
Stores sessions using keys like `session:${id}`. This lacks isolation and namespace structure, which can cause namespace collision on shared Redis servers.

### Browserbase Research
Stubbed. No real web connection, scraping, or search navigation is performed.

### Simular / SimuLang Desktop Context
Proposes a static list of mouse-clicks. No real screen positioning or safe execution occurs.

### Fetch-style Agent Routing
Currently local. Dispatches strictly using regex checks against the question text.

### Arize Tracing & Sentry Monitoring
Completely missing. No logging to Arize, no performance monitoring, and no global error handler captures renderer or main process exceptions.

### Privacy and Safety
The app title checks are basic and run on primary screen names instead of searching window titles of active processes.

## 4. Remove-List

The following items are out of sponsor scope, fake, or block the core tutor loop. They will be removed or deactivated:
- **Excluded Sponsors**: Any code references, comments, or stubs mentioning QNX, Zoox, Cognition / Devin, Annapurna Labs / AWS, Poke / Interaction Co.
- **OpenAI and Gemini Providers**: Deactivate/ignore these providers. Maintain only Claude (Anthropic) and Mock AI.
- **Rigid Keyword-only Mocks**: Refactor the mock provider to parse coordinates dynamically or return realistic structures.
- **Non-essential Settings**: Postpone generic dashboards or configuration screens. All development should focus on the core ScreenTutor loop.
